# 课小秘现有 API Agent 工具执行器设计

## 目标与明确边界

本设计让客服 Agent 直接复用 `LingKe.CApi` 与 `LingKe.CRMApi` 的现有 HTTP Action，不新增一套业务查询接口，也不让模型生成 SQL、拼接 URL、填写身份字段或接触签名凭据。

Agent 负责根据当前对话目标、已经取得的证据和仍缺少的事实动态选择能力；运行层只负责能力检索、权限校验、参数绑定、HTTP 调用、响应投影和审计。不得建立“问题关键词 → 固定接口 → 固定答案”的路由表。

本阶段只生成机器目录和执行器设计：

- 不注册运行时工具。
- 不调用真实 C/B API。
- 不修改 `LingKe.CApi` 或 `LingKe.CRMApi`。
- 不默认启用任何候选 Action。

## 已确认的现有基础

1. DuckAI 的 `CustomerServiceAgentV2ToolRegistry` 已采用“模型决定调用什么，注册表负责能力发现和安全执行”的结构，并明确禁止在 Agent 循环增加关键词分支。现有 API 能力应沿用这一结构。
2. 两端 API 均是 `.NET 8` ASP.NET Core Controller API，公共路由为 `api/[controller]/[action]`。
3. C 端认证过滤器使用现有用户登录 Token；商家端使用现有商家登录 Token，并检查请求正文中的 `Uid`、请求头身份及门店关系。
4. 两个项目源码配置中的 `ApiIsChecked` 当前均为 `false`。这只是源码配置事实，不代表生产覆盖值；AI 专用部署不能在未验证入口隔离时依赖该默认值。
5. Markdown 目录中的“使用时机”是帮助人工理解能力的示例，不是运行时路由规则。机器目录不保存特定用户问题、触发关键词或固定回答。

## 机器目录

- 顾客视角：`capi-api-tool-manifest.json`
- 商家视角：`crmapi-api-tool-manifest.json`

两份文件由 `build_api_tool_catalog.py` 从 Controller、DTO、继承字段、`if` 校验和一层 Provider/Service 调用确定性生成，不能手工维护第二份接口定义。

每个工具记录包含：

- 稳定 `toolId`、视角、业务域和能力摘要。
- 现有 HTTP 方法、路由、绑定方式和认证类型。
- 完整请求字段、源码必要性证据和字段来源策略。
- 只允许模型填写的简单业务参数 Schema。
- 必须由服务端上下文、当前会话敏感值或上游引用补齐的字段。
- 响应包装、字段投影、个人信息、内部引用和凭据阻断策略。
- Controller 校验、直接业务调用、失败信号、时效边界和 C/B 对照接口。
- A/B/C 等级、人工复核状态和运行时白名单要求。

所有记录默认 `defaultEnabled=false`。D 级 Action 不进入机器目录；C 级只能用于人工审查，不能注册为运行工具。

## Agent 动态调用模型

运行时只增加两个通用元工具，不为会员卡、预约、消费或未来新增业务分别写 Agent 分支。

### `search_existing_api_capabilities`

作用：根据 Agent 当前调查目标和证据缺口，从 C/B 机器目录检索少量候选能力，只返回能力契约，不读取客户数据。

建议输入：

```json
{
  "query": "当前需要证实的业务事实和已有证据缺口",
  "perspective": "customer|merchant|either",
  "limit": 8
}
```

约束：

- `query` 是自然语言调查目标，不是固定分类枚举。
- `perspective` 只缩小视角，不授予身份权限。
- 召回同时使用能力摘要、业务域、请求字段说明和允许输出字段说明，不使用手工问题关键词表。
- 只返回当前部署白名单中的 A/B 级工具；C/D 级不得进入模型候选。
- 返回候选的 `toolId`、能力说明、所需上下文、可填参数 Schema、响应证据范围和 C/B 对照关系。

### `invoke_existing_api_capability`

作用：执行最近一次能力检索实际返回的一个 `toolId`。

建议输入：

```json
{
  "toolId": "最近一次能力检索返回的编号",
  "arguments": {},
  "references": {}
}
```

约束：

- `toolId` 必须存在于当前会话最近一次能力检索结果、部署白名单和相同视角权限中。
- `arguments` 只接受清单 `agentArgumentSchema` 声明的普通业务参数；拒绝额外字段。
- `Uid`、`StoreId`、`AppId`、手机号、签名和真实内部 ID 不出现在模型参数 Schema 中。
- `references` 只接受执行器先前签发的短期不透明引用，例如 `R1`；模型不能提交真实主键。
- 执行器重新验证会话、门店、目标会员和工具等级，不能因为 Agent 已选择工具而跳过授权。

## 参数来源模型

| `sourcePolicy` | 来源 | 模型权限 |
| --- | --- | --- |
| `operator-context` | 当前已验证商家操作人 | 不可见、不可覆盖 |
| `customer-context` | 当前门店内已解析的目标会员 | 不可见、不可覆盖 |
| `store-context` | 当前已确认门店 | 不可见、不可覆盖 |
| `application-context` | 当前产品和小程序配置 | 不可见、不可覆盖 |
| `conversation-sensitive-context` | 当前请求临时保存的手机号等敏感值 | 模型只知道“已提供”，不接收原值 |
| `upstream-reference` | 前一步成功结果生成的短期引用 | 模型只能传 `R*`，不能传真实 ID |
| `model-argument` | 日期、分页、状态、排序等普通业务条件 | 只能按动态 Schema 提交 |
| `forbidden` | Token、签名、随机密钥等凭据 | 永不接受、永不返回 |

## C/B 身份与视角切换

商家视角始终以已验证操作人和门店为边界。顾客视角不能简单地把商家 UID 替换成会员 UID：执行器必须先在当前门店范围内解析目标会员，并建立独立的 `customer-context`。

手机号处理规则：

1. 原始手机号由客服会话运行层临时保存，模型上下文只出现“已提供会员手机号”。
2. Agent 动态检索能够定位主体的商家端能力；调用时执行器把手机号绑定到 `conversation-sensitive-context`。
3. API 成功响应中的会员、卡或其他内部 ID 不直接交给模型，而是转换为当前会话短期引用。
4. 后续顾客端能力需要 `Uid` 或业务 ID 时，由执行器从引用表绑定。
5. 未找到、同门店多义、跨门店冲突或关系失效时停止切换，返回证据不足观察，不猜测目标主体。

这是一条通用的“上下文解析 → 能力检索 → 受控执行 → 引用传递”机制，不针对某个固定客服问题。

## 直接调用现有 API

执行器通过 `IHttpClientFactory` 分别使用 `capi-ai` 与 `crmapi-ai` 客户端，BaseAddress 来自私有运行配置。模型和机器目录中均不保存主机名或凭据。

每次调用：

1. 根据 `toolId` 取机器契约，拒绝不在部署白名单或不是 A/B 级的工具。
2. 重新验证操作人、门店、产品以及可选的目标会员上下文。
3. 合并模型普通参数、服务端上下文和上游引用，生成现有 Action 的请求正文。
4. 使用现有 API 的签名头协议或 AI 专用隔离部署的受控入口调用原路由，不新增业务查询 Action。
5. 先检查 HTTP 结果和 `DataResult/DataList` 的 `State/StatusCode/Message`，失败只形成工具观察。
6. 按清单字段投影响应：凭据阻断、个人信息最小化、内部 ID 转为短期引用。
7. 生成 `T*` 证据记录，包含工具编号、视角、调用时点和可证明字段，不包含 URL、签名、手机号、请求正文或原始完整响应。

禁止自动重试具有不确定副作用的请求。即使 A/B 级查询也只允许一次受控重试网络连接失败，并且必须使用新的 `requestId/nonce`；业务失败、超时后未知状态和 C 级接口均不自动重试。

## 认证部署方案与待验证假设

### 方案一：复用现有签名认证

执行器使用现有登录 Token 生成 C/B API 已支持的请求头和签名，不增加新认证协议。

需要先验证：

- 企微客服身份解析得到的商家操作人在没有打开商家端时，是否仍有可用的现有商家登录 Token。
- 目标会员当前没有打开顾客端时，是否仍能取得可用的 C 端登录 Token。
- 平台值、请求正文序列化和 `ParamsHelper.GetParams` 是否能与现有客户端签名完全一致。

任一条件不成立，就不能假装可以直接调用。

### 方案二：AI 专用隔离部署复用原路由

部署相同 CAPI/CRMAPI 代码，仅允许 DuckAI 执行器经私网或双向 TLS 访问，并由反向代理只放行已验收的 A/B 路由。

注意：仅设置 `ApiIsChecked=false` 不构成安全隔离，因为同一应用仍包含写 Action。必须同时满足：

- 不公开暴露主机。
- 反向代理按“HTTP 方法 + 精确路径”白名单放行。
- DuckAI 运行白名单与代理白名单来自同一已验收清单并校验源码指纹。
- C/D 级和所有未收录新 Action 默认拒绝。
- 使用独立日志、限流、超时和网络身份；不得复用客户可访问入口。

该方案没有新增 HMAC 查询入口，业务仍由现有 Action 处理，但部署边界必须先经过安全验收。

## 最小验证实验

在实现真实 HTTP 执行前，只改变“认证方式”这一个变量：

1. 选取一个已静态确认无副作用、参数最少的 B 级商家端 Action，以及一个同条件的 C 端 Action。
2. 使用测试门店、测试操作人和测试会员，分别验证现有签名认证能否在没有用户当前打开客户端的情况下成功。
3. 成功信号：身份过滤通过、`State=true`、门店和目标主体正确、日志不含敏感值。
4. 失败信号：Token 不存在/失效、签名不一致、主体或门店校验失败。
5. 只有实验失败时才转向 AI 专用隔离部署；不能同时改变认证、路由和业务请求后再猜原因。

## 后续实现分层

沿用当前 DuckAI 分层，不在 Controller 或 Agent 循环堆叠业务判断：

- `SkillApiToolCatalog`：加载、校验和按语义检索机器目录。
- `SkillApiToolPolicy`：验证产品、视角、等级、部署白名单、参数来源和最近检索证明。
- `SkillApiContextResolver`：绑定操作人、门店、目标会员、敏感会话值和短期引用。
- `SkillApiHttpExecutor`：构造现有 API 请求、认证、超时和响应包装检查。
- `SkillApiResponseProjector`：按字段策略脱敏并签发引用。
- `SkillApiAuditWriter`：记录安全调用摘要和 `T*` 证据元数据。
- `CustomerServiceAgentV2ToolRegistry`：只注册两个通用元工具，不感知会员卡、预约或其他具体业务域。

新增公开类型、配置字段和业务安全判断必须写中文注释；复用现有 `CustomerServiceAgentV2ToolRegistry` 的工具循环、轮次限制、重复调用防护及证据引用机制。

## 验收标准

- 代码和配置中不存在用户问题关键词到 `toolId` 的映射。
- 新增业务 Action 后只需重新生成目录，不需要修改 Agent 分支。
- 模型无法提交 `Uid/StoreId/AppId`、原始手机号、签名、Token 或真实内部主键。
- 只有最近能力检索返回且部署白名单启用的 A/B 工具可执行。
- C/B 视角分别授权，顾客上下文只能在当前门店内解析。
- D 级工具不进入机器目录，C 级默认不可执行。
- 响应只返回完成本轮调查所需的字段；个人信息最小化、凭据阻断、内部 ID 引用化。
- 每个结论都能回指成功工具证据；空结果、失败结果和当前状态不能被扩写为未证明原因。
- 目录源码指纹变化但未重新生成或未重新验收时，启动失败而不是继续使用旧白名单。
